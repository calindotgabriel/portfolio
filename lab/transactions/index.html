Two hundred transfers, none of them failed

Three accounts holding 1,000 each. Two hundred transfers between them, all at once. Every transfer reports success, nothing raises an error, and the accounts end up holding 3,296. Run it below, then run the fixes and see what each costs.

Live demo PostgreSQL postgres-isolation-lab ↗

What goes wrong

Moving money is four steps: read the sender's balance, check there is enough, take it off one account, add it to the other. Run two transfers at once and those steps overlap. Both read 1,000. Both write back a number they worked out from it. The second lands on top of the first.

Nothing here is invalid, so nothing complains. What is wrong is the relationship between two writes, and no single statement can see that. It turns up weeks later as an account that is short, in a log full of successful transfers.

Show the six lines that do it 
const from = await db.read(t.from);
const to = await db.read(t.to);
if (from.balance < t.amount) throw new Error("insufficient funds");

await db.write(t.from, from.balance - t.amount, from.version);
await db.write(t.to, to.balance + t.amount, to.version);

Run it

The accounts below are plain JavaScript objects, and every read and write waits a real turn of the event loop before it lands — so twenty transfers in flight genuinely interleave. Both buttons run the same list. Only one ends with the money adding up.

The third fix — serializable, and the retries it costs

Instead of locking, the database lets every transaction read freely and checks at commit whether a row it read has changed since. If one has, the transaction is thrown out with 40001. Nothing is wrong with your code — the contract is that you run the whole thing again.

Two transactions that are each correct and together wrong

Two doctors are on call. Either may go off call provided somebody else is still on. Both check at the same moment, both see two on call, both go off. Nobody overwrote anybody, and there is no doctor on call.

This is write skew, and it survives the fixes above: neither transaction touched a row the other touched, so watching for overwritten rows catches nothing. Serializable catches it because it tracks what a transaction read, not only what it wrote.

Deadlock, and the one line that fixes it

Locking only works if everyone agrees on an order. A transfer from account 1 to 2 locks 1 then 2; one going the other way locks 2 then 1. Each ends up holding what the other is waiting for, and the database kills one with 40P01. Sorting the ids before locking fixes it.

On Postgres that sort() was the difference between 70,504 ms and 96 ms for the same 40 transfers — 142 deadlocks against none, because Postgres waits a full second before it even looks for a cycle.

The fixes, and what they cost

Three of them, in the order I would reach for them. The first is both the cheapest and the most limited.

01

Let the database do the arithmetic

UPDATE accounts SET balance = balance - $1 never sends a balance through the application, so nothing can go stale on the way. Cheapest and fastest — but it only works when the new value is a function of the old one.

Show it in code 
-- One statement. Postgres locks the row, reads it and
-- writes it without letting anyone in between.
UPDATE accounts
   SET balance = balance - $1
 WHERE id = $2
   AND balance >= $1;

-- The funds check rides along in the WHERE clause,
-- so it cannot be true at read time and false at
-- write time. Zero rows updated = insufficient funds.
02

Lock the rows first

SELECT … FOR UPDATE takes the locks up front and holds them to the end, leaving no gap for anyone to write into. For when the decision really does need a read first. The cost is waiting.

Show it in code 
BEGIN;

-- Take both row locks before reading anything, and
-- always lowest id first: an order every transfer
-- agrees on is what stops two of them deadlocking.
SELECT balance FROM accounts WHERE id = $lo FOR UPDATE;
SELECT balance FROM accounts WHERE id = $hi FOR UPDATE;

-- Nobody else can read or write these rows now, so
-- deciding in application code is safe here.
UPDATE accounts SET balance = balance - $amt
 WHERE id = $from;
UPDATE accounts SET balance = balance + $amt
 WHERE id = $to;

COMMIT;
03

Serializable, and retry

The database throws out anything it could not have run in some serial order. Correctness moves into the database; running the whole thing again moves into your code. Skip the retry and most of the work never happens.

Show it in code 
for (let attempt = 1; ; attempt += 1) {
  try {
    await client.query("BEGIN ISOLATION LEVEL SERIALIZABLE");
    // read freely, decide, write
    await client.query("COMMIT");
    return;
  } catch (err) {
    await client.query("ROLLBACK");

    // 40001 could not serialize, 40P01 deadlock victim.
    // Neither is a bug. Both mean: run it again.
    if (!RETRYABLE.has(err.code) || attempt >= 5) throw err;

    // Back off with jitter, or the retries collide too.
    await sleep(Math.random() * 10 * 2 ** attempt);
  }
}

The browser demo is a model; the table is measured. PostgreSQL 16.15 in Docker, the same three accounts, 200 concurrent transfers over a pool of 20, each row one run at a different setting. It is a repo, so you can disagree with it by running it.

Version Wall Committed Thrown out Total after
Arithmetic in the app 176 ms 200 / 200 0 3,011
balance = balance - $1 170 ms 200 / 200 0 3,000
SELECT … FOR UPDATE 254 ms 200 / 200 0 3,000
Serializable, with retry 398 ms 137 / 200 659 3,000
Serializable, no retry 83 ms 26 / 200 174 3,000

The first row is the bug: fastest, no errors, wrong answer. The second is the one worth knowing — letting the database do the arithmetic was correct and as fast as the broken version, 170 ms against 176.

Serializable is the row worth sitting with. It got the right total by throwing out 659 transactions to land 200 transfers, and 63 of them never happened at all. That is partly the five-attempt retry cap and mostly the workload: every transfer here touches two of only three rows. Spread them over ten thousand accounts and the retry rate falls close to nothing.

What this does not prove

The thing in your browser is not Postgres — no snapshots, no write-ahead log, no planner, no disk. It models the interleaving and one commit-time rule, and it overstates the damage: Postgres holds a row lock for the duration of an UPDATE even with no transaction around it, so its window is narrow where the model's is the whole gap between a read and a write. That is the browser losing about 300 out of 3,000 against Postgres losing 11.

The browser is also reproducible in a way the database is not. Five consecutive Postgres runs of the identical 200 transfers finished at 3,005, 3,008, 3,009, 3,013 and 3,019 — same code, same input, a different wrong answer each time.
